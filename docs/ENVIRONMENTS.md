## 数据与配置边界

这些站点沿用现有 Supabase 账号、教师资料和报告数据。不能把 Preview 当作安全的测试数据库：若配置指向同一 Supabase 项目，创建账号、重置密码、修改资料等操作会影响共用数据。交接时逐环境核对 Supabase 项目标识；核对结果只记录项目标识，不记录密钥。

每套部署独立配置环境变量，不能因为一个站点能登录就认定其他站点配置正确：

- `NEXT_PUBLIC_SUPABASE_URL`、`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`：登录及数据库客户端配置，须属于同一 Supabase 项目。
- `SUPABASE_SERVICE_ROLE_KEY`：师资管理等受保护的服务端管理操作需要。只配置在受保护的服务端，禁止浏览器暴露、Git 提交或写入交接文档。
- `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL`：服务端生成配置；不同环境应分别核对。

变量修改后需要重新构建、部署并验收。Vercel 的 Production、Preview、Development 配置范围还需分别确认。

## 发布流程

1. 确定目标环境，核对分支、工作区和待发布提交。保留用户未提交文件；原目录的 `tsconfig.tsbuildinfo` 和 `docs/PROJECT_HANDOFF.md` 不纳入无关提交。
2. Vercel 修改提交至 `main` 后检查自动部署结果。该动作不会同步 Netlify。
3. Netlify 发布前将确认的修改同步到 `netlify`，完成测试后再构建部署。不要为每个小改动触发 Netlify 发布。
4. Preview 如需更新，应明确指定其别名，不能误用生产发布选项覆盖正式站。发布前核对其数据库配置与测试账号。
5. 验收登录、教师资料、生成、历史读取、修改保存和 PDF；隔离模拟测试不能替代真实服务验收。记录环境、分支、提交、部署 ID、验收时间及其他环境是否同步。

## 故障交接信息

记录网址、发生时间及其时区、问题编号、操作环节和对应部署版本。错误提示相同不代表根因相同；请求超时不能证明报告丢失，生成失败不能直接归咎于教师输入。浏览器侧编号未必代表服务端已经收到请求，需结合平台请求日志核实。
